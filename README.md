# Учёт техники

Приложение для учёта техники: серверная часть на ASP.NET Core 8 (Web API, EF Core, PostgreSQL) и
веб-интерфейс на React. Развёртывается в Docker (backend, frontend и изолированная база данных
в отдельных контейнерах).

## Состав

- **backend/EquipmentTracker.Api** — ASP.NET Core 8 Web API, EF Core (Npgsql), JWT-аутентификация.
- **frontend** — React + TypeScript + Vite, раздаётся через nginx.
- **docker-compose.yml** — оркестрация сервисов: `db` (PostgreSQL, без внешнего порта — изолирована),
  `backend`, `frontend`, `backup` (ежедневные зашифрованные копии БД, см. «Резервное копирование»).

## Модель прав доступа

**Анонимного доступа нет:** без входа доступна только страница входа, все данные и экспорт требуют
авторизации. У учётной записи должна быть хотя бы одна роль (запись без ролей ничего не видит).

| Действие                                                                   | Требуемая роль                        |
|-----------------------------------------------------------------------------|----------------------------------------|
| Просмотр: главная, карточки техники, ремонты, справочники, списания, история, экспорт (Excel/QR) | любая: «Только чтение», Оператор, Администратор |
| Создание/редактирование/удаление/перемещение техники, локаций, справочников; фиксация ремонтов и выдач; пополнение запаса | Оператор или Администратор |
| Прямая установка остатка, удаление расходных частей, изменение/отмена списаний | Администратор |
| Запуск и остановка инвентаризации; изменение/удаление ремонтов и выдач | Администратор |
| Подтверждение данных о технике в ходе инвентаризации | Оператор или Администратор |
| Создание/редактирование/удаление учётных записей                            | Администратор                          |

Роль «Только чтение» (`Viewer`) ничего изменять не может: кнопки редактирования ей не показываются,
а сервер отклоняет такие запросы (403).

При первом запуске автоматически создаются роли `Viewer`, `Operator`, `Administrator` и стандартная
учётная запись администратора (логин/пароль — из `.env`, см. ниже). **Обязательно смените пароль
администратора после первого входа** через раздел «Учётные записи».

## Быстрый старт

1. Скопируйте `.env.example` в `.env` и задайте свои значения (пароль БД, JWT-секрет, пароль
   администратора):

   ```bash
   cp .env.example .env
   # отредактируйте .env
   ```

   Секрет для JWT можно сгенерировать так: `openssl rand -base64 48`.

2. Соберите и запустите контейнеры:

   ```bash
   docker compose up --build -d
   ```

3. Откройте фронтенд в браузере: `http://localhost` (порт задаётся `FRONTEND_PORT` в `.env`, по
   умолчанию 80). API доступен по тому же адресу под `/api/` (nginx проксирует его на бэкенд);
   порт бэкенда наружу не публикуется.

4. Войдите под учётной записью администратора (логин/пароль из `.env`), смените пароль,
   создайте нужных пользователей с ролями «Оператор» и заполните справочники (типы и наименования
   техники), затем локации и единицы техники.

## HTTPS (сертификат на IP-адрес)

Сайт может работать по HTTPS без домена — с бесплатным сертификатом Let's Encrypt на IP-адрес сервера.
Такие сертификаты действуют ~6 дней, поэтому всё автоматизировано: сервис `certbot` выпускает сертификат и
каждые 12 часов проверяет, не пора ли продлить (продлевает примерно за 3 дня до истечения), а nginx
фронтенда сам подхватывает новый сертификат без перезапуска. HTTPS нужен, например, для сканирования
QR-кодов камерой в реальном времени.

Требования: у сервера публичный IP, порты **80 и 443 открыты из интернета** (Let's Encrypt проверяет сервер
по порту 80, поэтому `FRONTEND_PORT` должен остаться 80).

1. В `.env` задайте `TLS_IP=<внешний IP сервера>` и для начала `TLS_STAGING=1` (тестовый сервер Let's
   Encrypt — не расходует лимиты, но сертификату браузеры не доверяют):

   ```bash
   docker compose up --build -d
   docker compose logs -f certbot     # ждём «Сертификат в порядке»
   docker compose logs frontend | grep 40-tls   # через ≤5 мин: «конфигурация перечитана (режим: https)»
   ```

   Сайт по `https://<IP>` откроется с предупреждением о недоверенном сертификате — так и должно быть.
2. Поставьте `TLS_STAGING=0` и выполните `docker compose up -d` — настоящий сертификат выпустится
   автоматически, через несколько минут сайт откроется по HTTPS без предупреждений.

Запросы по `http://` перенаправляются на `https://` с тем же путём, поэтому напечатанные ранее QR-коды со
ссылками продолжают работать. Пока сертификата нет (или `TLS_IP` пуст), сайт работает по HTTP, как раньше.

Если продление не удаётся, приходит письмо (те же настройки `BACKUP_NOTIFY_TO`/`BACKUP_SMTP_*`, что для
резервного копирования) — сразу и затем раз в сутки, пока не заработает; после восстановления — письмо
«снова работает». Частые причины сбоя — закрытый снаружи порт 80 или остановленный контейнер `frontend`.

## О миграциях базы данных

Схема БД управляется миграциями EF Core (`backend/EquipmentTracker.Api/Migrations`); при старте
backend вызывает `MigrateAsync()` в `Data/DbInitializer.cs`.

## Перенос данных из старой программы (Hardware)

Скрипт `tools/import-hardware.sh` переносит данные из дампа MySQL старой программы (файл, созданный
`mysqldump`, например `dump-hardware-….sql`):

| В старой программе                        | В этом приложении                                  |
|-------------------------------------------|----------------------------------------------------|
| типы устройств                            | типы техники                                       |
| наименования устройств                    | наименования техники                               |
| здания → кабинеты → комплекты             | вложенные локации: здание → кабинет → комплект     |
| устройства (серийный, инвентарный номер, примечание) | единицы техники в локации своего комплекта |

Поставщик устройства не переносится (в приложении такого поля нет), история и ремонты старой программы —
тоже. В истории изменений перенесённые записи отмечены как созданные пользователем «импорт из Hardware».

Импорт **дополняет** существующие данные и не создаёт дублей:

- типы и наименования сопоставляются по названию (без учёта регистра) — существующие используются как есть;
- здание ищется среди локаций верхнего уровня, кабинет — внутри здания, комплект — внутри кабинета;
- техника, чей серийный номер уже есть в базе, пропускается (об этом выводится сообщение).

Поэтому скрипт можно безопасно запустить повторно. Всё выполняется одной транзакцией: при любой ошибке
в базе ничего не меняется.

### Как перенести

Все команды выполняются на сервере в папке проекта (где лежит `docker-compose.yml`). Приложение должно быть
запущено хотя бы один раз, чтобы в базе были созданы таблицы.

1. Скопируйте дамп на сервер в папку проекта (в git он не попадёт — `dump-*.sql` в `.gitignore`), например:

   ```bash
   scp dump-hardware-….sql user@<IP-сервера>:/путь/к/EquipmentTracker/
   ```

2. Сделайте резервную копию текущей базы:

   ```bash
   docker compose exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" "$POSTGRES_DB"' | gzip > before-import.sql.gz
   ```

3. Запустите перенос (останавливать приложение не нужно):

   ```bash
   sh tools/import-hardware.sh dump-hardware-….sql \
     | docker compose exec -T db sh -c 'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
   ```

   В конце выводится таблица «В дампе / Создано» по типам, наименованиям, локациям и технике. Над ней могут
   быть сообщения `NOTICE` — о пропущенной технике (серийный номер уже есть) и о наименованиях, которые уже
   были в базе с другим типом (тип остаётся прежним).

4. Откройте главную страницу и проверьте дерево локаций.

5. Удалите с сервера дамп и `before-import.sql.gz` (в них персональные данные) — после того как убедитесь,
   что всё перенеслось.

Если нужно откатить перенос, восстановите копию из шага 2:

```bash
docker compose stop backend
docker compose exec -T db sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "DROP SCHEMA public CASCADE; CREATE SCHEMA public;"'
gunzip -c before-import.sql.gz | docker compose exec -T db sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
docker compose start backend
```

Чтобы посмотреть SQL, который будет выполнен, не трогая базу: `sh tools/import-hardware.sh dump-hardware-….sql > import.sql`.

## Резервное копирование

Сервис `backup` каждый день (в `BACKUP_HOUR`, по умолчанию 03:00 по Москве) делает дамп БД,
сжимает его, **шифрует** и выгружает на Яндекс Диск (WebDAV). Последние `BACKUP_KEEP_LOCAL` копий
остаются на сервере (том `backup-data`), на диске копии хранятся `BACKUP_KEEP_REMOTE_DAYS` дней.
Все настройки, включая папку на диске, задаются в `.env` (переменные `BACKUP_*`, см. `.env.example`).

### Настройка (один раз)

1. **Ключ шифрования.** На любой машине с Docker (не на сервере):

   ```bash
   docker run --rm alpine sh -c "apk add -q age && age-keygen"
   ```

   Команда выведет `Public key: age1…` и приватный ключ `AGE-SECRET-KEY-…`. Публичный ключ впишите в
   `BACKUP_AGE_PUBLIC_KEY`, а **приватный сохраните в надёжном месте вне сервера** (например, в
   менеджере паролей). Без него копии не расшифровать, а на сервере он не хранится.
2. **Пароль приложения Яндекса.** Войдите в почту → Яндекс ID → «Безопасность» →
   «Пароли приложений» → тип «Файлы WebDAV». Логин (`BACKUP_WEBDAV_USER`) — полный адрес почты,
   пароль (`BACKUP_WEBDAV_PASSWORD`) — созданный пароль приложения, а не пароль от почты.
3. Заполните `BACKUP_REMOTE_DIR` (папка на диске, создаётся автоматически) и запустите:

   ```bash
   docker compose up --build -d
   docker compose logs backup      # должно быть «Резервное копирование включено»
   docker compose run --rm backup /app/backup.sh   # пробная копия прямо сейчас
   ```

   Пока настройки копирования (ключ и данные Яндекс Диска) не заданы, контейнер `backup` просто
   простаивает: пишет в лог «не настроено», ничего не делает и остальную систему не затрагивает.
   Если заполнена только часть настроек, он сообщает об ошибке в логе.

### Уведомления о сбоях

Если задан `BACKUP_NOTIFY_TO` (адреса через запятую), при неудачной копии приходит письмо с
последними строками журнала, а когда копирование снова заработает — письмо «снова работает».
Если копия не создаётся несколько дней подряд, письмо приходит каждый день. Настройки SMTP —
`BACKUP_SMTP_*` (для Яндекс Почты по умолчанию `smtp.yandex.ru:465`, логин — адрес ящика,
пароль — отдельный «пароль приложения» типа «Почтовые клиенты», не тот, что для WebDAV).
Проверить отправку: `docker compose run --rm backup /app/notify.sh "Проверка" "Тестовое письмо"`.
Если `BACKUP_NOTIFY_TO` пуст, уведомления отключены (копирование при этом работает) и о сбоях можно узнать только из логов
(`docker compose logs backup`).

Письмо не придёт, если не работает сам сервер или контейнер `backup` остановлен — такие случаи
письмом не отследить.

Также сохраните вне сервера копию `.env` (`JWT_SECRET`, пароль БД): в дампе их нет.

### Восстановление

Копию скачайте с Яндекс Диска (файл `equipment-tracker-….sql.gz.age`), затем:

```bash
# 1. Расшифровать и распаковать (key.txt — файл с приватным ключом)
docker run --rm -i -v "$PWD/key.txt:/k:ro" alpine sh -c "apk add -q age && age -d -i /k | gunzip" \
  < equipment-tracker-….sql.gz.age > dump.sql

# 2. Остановить приложение и загрузить дамп (подставьте значения из .env)
docker compose stop backend backup
docker compose up -d db
docker compose exec -T db psql -U <POSTGRES_USER> -d <POSTGRES_DB> < dump.sql

# 3. Запустить всё обратно
docker compose up -d
```

Дамп содержит `DROP … IF EXISTS`, поэтому его можно загружать и поверх существующей базы, и в пустую
базу на новом сервере. Проверять восстановление на тестовом стенде стоит хотя бы раз, чтобы не
узнать о проблеме в момент аварии.

## Инвентаризация

Страница «Инвентаризации» (видна всем ролям) — список инвентаризаций: начало, окончание, статус и
процент завершённости (сколько техники из общего числа подтверждено). Одновременно идёт не более одной.

- **Запуск/остановка** — Администратор. Пока инвентаризация идёт, на главной странице и в карточках
  техники показывается плашка «Идёт инвентаризация», а вся техника помечена: ● — не подтверждена,
  ✔ — подтверждена. Локации тоже помечены (✔ — вся техника внутри подтверждена, включая вложенные
  локации; ● — есть неподтверждённая).
- **Подтверждение данных и его отмена** — Оператор и Администратор («Только чтение» не подтверждает): в карточке
  кнопка «Подтвердить данные»; на главной странице — «Подтвердить» для выделенного (можно много
  записей сразу; выделенная локация подтверждает всю технику внутри); «Снять подтверждение» отменяет
  ошибочное подтверждение (в карточке — «Отменить подтверждение»).
- **Новая техника**, добавленная в ходе инвентаризации, считается неподтверждённой; удалённая
  выпадает из подсчёта. Правка или перемещение подтверждение не сбрасывают.
- **Остановка** убирает индикацию и кнопки. Итоги сохраняются как есть на момент остановки (даже если
  технику потом удалят или изменят): «Итоги» → сколько подтверждено/не подтверждено, список
  неподтверждённой техники и её выгрузка в Excel (формат как у списка техники на «Экспорте»).

## Сканер QR-кодов

Страница «Сканер» (все роли) открывает карточку техники по QR-коду: подходят коды с данными
этого приложения и коды из старой программы (поиск по серийному номеру), а также напечатанные ранее
коды-ссылки на карточку (сейчас такие коды больше не генерируются). Способы:

- **«Сфотографировать QR-код»** — на телефоне открывает камеру, код распознаётся на снимке. Работает и по HTTP.
- **Поле ввода** — серийный номер вручную или USB/Bluetooth-сканер штрихкодов (работающий как клавиатура).
- **«Сканировать камерой»** (в реальном времени) — только если сайт открыт по HTTPS: без него браузеры не
  дают доступ к видеопотоку камеры, и кнопка не показывается.

## Главная страница (дерево локаций/техники)

Главная страница состоит из двух рабочих областей (левая и правая), в каждой — сворачиваемое
дерево локаций с вложенными единицами техники (в духе Total Commander):

- Перетаскивание (drag-and-drop) локации или единицы техники на другую локацию — перемещает её
  внутрь (родительская локация / расположение техники меняются).
- Кнопки «Слева → Справа» / «Справа → Слева» на панели инструментов перемещают выбранный элемент
  одной панели в локацию, выбранную в другой панели — без необходимости перетаскивать мышью.
- Узел «Без локации» — виртуальный контейнер для техники, не привязанной ни к одной локации.
- Кнопки создания/редактирования/удаления доступны только пользователям с ролью «Оператор» или
  «Администратор»; роли «Только чтение» видна только структура дерева (без изменений).

## История изменений

Любое создание, изменение или удаление локации, типа техники, наименования техники или единицы
техники автоматически фиксируется в таблице истории (`EditHistoryEntry`) — кто, когда и что
изменил (JSON со старыми/новыми значениями полей). Просмотр — на странице «История», доступен
Операторам и Администраторам.
